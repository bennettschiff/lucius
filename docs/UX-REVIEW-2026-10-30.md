# Lucius UX review — October 30, 2026

## Product direction

Lucius is most useful when it helps someone choose a sensible check, understand the evidence, and take a deliberate next step. Its distinctive component map is worth keeping, but it should not be the only starting point for someone who simply knows their Mac feels wrong.

This pass turns the existing collection of tools into a guided workflow while preserving on-demand operation, bounded resource use and explicit recovery controls. It does not introduce a health score, automatic repairs, background polling, AI services or claims of complete hardware coverage.

## Findings and delivered changes

| Priority | Finding | Implemented response |
| --- | --- | --- |
| High | Opening into a six-component scan made users choose a technical subsystem before they understood the symptom. “Scan my Mac” overstated that scope. | Default Checkup workspace; Quick and Extended plans with coverage stated before starting. Component action renamed “Scan components.” |
| High | No way to run the existing checks as one coherent workflow. | Sequential guided runner: components → system categories → optional bounded hardware workloads. One owner, one cancel action, real stage progress. |
| High | A finished run could be confused with a clean bill of health, especially with missing observations. | Separate review, unavailable and partial coverage; all-unavailable runs say “No assessments available.” Hardware outcomes remain workload-specific. Missing/inactive components are not marked failed. |
| High | System reports vanished on quit, and History offered summaries without access to detailed reports. | Retain ten full checkups and ten system reports, alongside ten hardware reports. History opens reports; exports retain measurement evidence and coverage. |
| Medium | An older selected hardware report could reappear after starting a new run from the menu. | Move report selection to shared state and clear it when a new hardware run begins. History opens the intended report. |
| Medium | Navigation used bespoke buttons without native list selection or keyboard traversal. Settings was not visible in the main window. | Native source list grouped into Start, Tools and Library; Settings link; quick-checkup menu and Command-Shift-R shortcut. |
| Medium | Users could navigate away from active checks and lose the path back. | Global activity bar offers Show run as well as Stop. Starting competing checks remains disabled. |
| Medium | Small component labels and a vertically constrained layout impaired readability. | Raise 8–10 point scan/inspector labels to 11 points, keep action controls visible, make the component workspace scroll, reduce the minimum window size to 1040 × 700. |
| Medium | New-run controls competed with completed results; review findings were buried in category order. | Collapse optional new-run choices after a checkup, show the report summary immediately, promote review findings, and show unavailable counts on the relevant collapsed stage. |
| Medium | Persistence failures were visible only on selected screens. | Display persistence notices globally. |

## Flow and state design

- Quick checkup: six interface components, memory/thermal state, storage capacity and power. No CPU/RAM/GPU test workload.
- Extended checkup: quick coverage plus network interfaces, security settings, hardware inventory and four bounded hardware tests. The choice explicitly describes resource use before starting.
- A run remains owned until cancellation cleanup finishes. Completed stages stay in its report; the interrupted stage is Stopped, later stages Not started. Errors in independent checks remain Unavailable and do not hide later evidence. A stopped hardware workload ends the guided run.
- Reports are immutable observations from a stated time. Saved report selection never makes old process identity actionable for a restart; component recovery still requires a separate live scan and explicit confirmation.
- No attempt is made to reconstruct old full system reports from historical summaries. Only newly collected reports have the new persistence behavior.
- The existing light default, dark/system choices and reduced-motion behavior remain. No idle timer was added by the checkup view; elapsed updates exist only while work runs.

## Verification

- SwiftPM app and packaged helper build successfully with ad-hoc signing. Local package: `dist/Lucius.app`, version 0.4.
- XCTest: final suite runs 33 cases, with 32 passed, one opt-in hardware-load smoke skipped, and zero failures. Seven new cases cover exact coverage/order, no hardware in Quick, interruption preservation, real task cancellation, independent unavailable stages, all-unavailable messaging, and persisted hardware evidence/export dates.
- Live packaged UI: Quick completed; Extended completed all eleven stages, including CPU/RAM/GPU passes and cooling observations. Quick Look was unavailable on this host, and remained explicitly unavailable in the summary.
- Stop from History during Extended cooling preserved earlier hardware passes, recorded the incomplete cooling stage, and reaped its worker. Host process inspection found only the app afterward.
- Command-Shift-R, cross-workspace Show run, and Command-Q during a quick checkup were exercised. Host process inspection after quit found no Lucius app or worker.
- Checkup and system reports survived quit/relaunch. History and saved-report selectors expose full reports. Existing historical hardware reports remain readable.
- Native export produced `artifacts/Lucius-checkup.md` (ignored). Readback confirmed CPU/GPU outcomes, workload metrics, coverage and raw cooling readings.
- Default-window component and checkup layouts inspected visually; light and dark appearances checked, original Light preference restored. Native accessibility trees expose labels, selected navigation, progress, checkboxes and disclosure controls. This is not a complete VoiceOver usability audit.

## Highest-value next work

1. **Compare two runs.** Show changes in the same measurements with timestamps and explicit missing-data handling. This would help determine whether a symptom improved without inventing a health score or running continuously.
2. **A searchable report library.** Group all saved report types by date, with filters for review, unavailable and stopped outcomes. Current retention is intentionally small, so this is useful refinement rather than a prerequisite.
3. **Targeted follow-up from a finding.** Offer a longer component observation or a specific existing workload when the finding supports it. Define conservative mappings and avoid implying a diagnosis from CPU or one thermal snapshot.
4. **Accessibility and compact-window pass.** Test minimum-size layouts, Full Keyboard Access and VoiceOver with a real user flow; audit the remaining 10–12 point labels in older hardware/system cards. The current review verified default-window visuals and native accessibility exposure, not formal accessibility conformance.
5. **Hardware result density.** Separate next-run test selection from saved-result review more decisively, and consider a compact results list before charts. Keep workload coverage and unknown sensor capability visible.

Broader sensor compatibility, new network/device checks, signing and public distribution remain separate engineering work. Disk repair, generic cleanup, force termination of system components and unattended monitoring remain outside the accepted scope.
